# Rajadhani Invoice

A responsive sales-invoice interface based on the supplied reference. The current delivery is a working UI preview; the organization connection and custom-field mapping are intentionally left for later, as requested.

## Files to use

- `dist/InvoicePreview.html` — standalone, offline UI preview. Open in a browser. Uses clearly labelled fictional customers and items. Try searching **Malabar**, then select **SO-00124**, or search items such as **Premium** or **PEN**. Fill bill type, type and transport, then review the invoice. ERP saving is disabled in this preview.
- `dist/RajadhaniInvoice.zip` — Zoho ERP widget package generated by ZET. Contains no preview fixtures. Upload after configuring the connection below and rebuilding.
- `dist/InvoicePreview.png` — visual preview of a filled invoice.
- `app/` — editable widget source, with no frontend framework or runtime npm dependency.

## Interface

Customer search with keyboard navigation; ERP billing/shipping addresses; same-as-billing; customer GSTIN; invoice date; automatic invoice numbering; payment terms; salesperson; location; place of supply; bill type; sale type; bill creator; mobile and WhatsApp; shipping phone/GSTIN; item search by name/SKU; barcode-scanner keyboard input; stock and UoM; pieces per pack and derived piece quantity; order quantity/rate/tax editing; sales-order import; transport/agent/vehicle; remarks; invoice pending; discount; round off; tax summary; review before draft creation; start over; responsive mobile layout.

M Unit and Ratio come from item master custom fields. M Unit = Set uses a positive whole-number Ratio as pieces per pack; M Unit = Pieces uses 1. P. quantity = order quantity × pieces per pack. Amount = P. quantity × rate per piece. Discounts, estimated taxes and review amounts follow this calculation. Invalid or missing M Unit/Ratio blocks saving.

`itemFields.mu` and `itemFields.ratio` accept item custom-field API names, IDs or labels. If blank, the widget matches the item-master labels M Unit/MU and Ratio (case-insensitive, ignoring spaces and punctuation). When a selected item is an item variant, the widget also fetches its parent item master and merges the master custom fields before calculating pieces per pack.

`invoiceQuantityMode` needs explicit confirmation before live saving: `pieces` sends P. quantity and per-piece rate; `order` sends order quantity and an equivalent rate per set (per-piece rate × Ratio). It is intentionally blank pending confirmation of how stock is maintained. Preview uses `pieces`. Sales-order import is disabled in live mode until the order's unit semantics are confirmed; preview import remains available.

Taxes in the summary use the names and rates of selected ERP taxes, not an assumed CGST/SGST split. The preview has representative tax names. Final ERP calculation is authoritative. The widget estimates exclusive-of-tax invoices with a before-tax invoice-level discount. Complex tax, foreign-currency, serial/batch/storage allocations and customer-specific price-list workflows require the native ERP editor or further integration work.

Addresses are read from the customer record. Billing address is inherited by invoice creation; the selected shipping address is sent with the invoice. This widget does not edit the customer's master record.

## Connect later

1. In your Zoho ERP Developer Space / extension configuration, create and authorize a connection for ERP APIs. Enable the scopes needed to read contacts, items, taxes/settings, locations and sales orders, and to create invoices. Select actual available scope names in your tenant. The documented invoice-create scope is `ERP.invoices.CREATE`.
2. Paste the **exact generated connection JSON** into `usedConnections` in `plugin-manifest.json`. Do not fabricate this object or put access tokens in the files.
3. Set `connectionLinkName` in `app/config.json` to the generated link name. `organizationId` normally comes from the SDK at runtime; set it explicitly only if needed. The API base defaults to India's `https://www.zohoapis.in/erp/v3`. Use your actual data-center domain and adjust `whiteListedDomains` in the manifest if needed.
4. Fill each `customFields.<field>.id` with its actual **invoice custom-field ID**, not a display label. `required` controls required UI fields. Defaults follow the screenshot's required business fields. A non-empty field without a mapping blocks save rather than dropping the value. Mobile/shipping phone and invoice-pending are also custom-field mappings in this implementation. A customer source field can be supplied as `customerApiName` to copy an ERP customer custom value when that customer is selected.
5. Configure live choice lists in `lookupSources` for dropdowns. An unconfigured business field remains a text input. Example shape (replace all example names with your own actual module endpoint and response fields):

   ```json
   {
     "transport": {
       "path": "/YOUR_ACTUAL_MODULE_ENDPOINT",
       "key": "YOUR_RESPONSE_ARRAY_KEY",
       "idKey": "YOUR_VALUE_FIELD",
       "labelKey": "YOUR_DISPLAY_FIELD",
       "query": {}
     }
   }
   ```

   `idKey` must return the value your invoice custom field accepts (text for a text field; record ID for a lookup). Lookup sources are paginated and fetched through the ERP connection. Never use static demo choices in the live configuration. Salesperson defaults to `/salespersons`; because this endpoint is not fully specified in the public ERP API reference, verify its tenant response or override `lookupSources.salesperson` with `path`, `key`, `idKey`, and `labelKey`.
6. Set `itemFields.mu` and `itemFields.ratio` to their item custom-field API names or IDs. Confirm `invoiceQuantityMode` before saving real invoices.
7. If your organization requires a location, set `requireLocation: true`. Set `requireSalesperson` according to your billing policy.
8. Run `npm ci`, then `npm run build`. Install a supported current Node.js version. ZET 1.0.29 is pinned in the lockfile.
9. Upload **the newly rebuilt** `dist/RajadhaniInvoice.zip` through Sigma → extension → Configure → Upload Widget. The ZIP name contains letters only. The package uses `service: ERP`, matching the current ZET ERP template, and both `invoice.list.sidebar` and `invoice.creation.sidebar`, with `widget_type: modal`, so either sidebar entry opens the form in a popup.
10. Test in your own organization: customer/item lookups, business-field options, taxes and tax groups, multi-location behavior, sales-order linkage, invoice numbering, permissions, and final totals. No live organization was available during this build. Mock integration tests are not a substitute for that tenant check.

You can use the connection settings button for a temporary session override of link name and organization ID. Permanent deployment settings belong in the config and manifest. No credentials are saved in browser storage.

## Local development and verification

- `npm run preview` starts an HTTP server on port 5179. Open `/dist/InvoicePreview.html`.
- `npx zet run` serves the widget for Zoho Developer Mode. Verify the local manifest at `https://127.0.0.1:5000/plugin-manifest.json`, then enable Developer Mode in ERP and open the widget in the new-invoice sidebar.
- `npm run build` runs `zet validate` and `zet pack`, and creates the standalone preview.
- `node --test tests/core.test.mjs` tests totals, validation, IDs, custom-field mappings and response handling.
- `npx playwright install chromium`, then `npx playwright test` while the preview server runs, tests browser flows. If using a custom `PLAYWRIGHT_BROWSERS_PATH`, pass it consistently for installation and execution.

Save semantics: the user reviews and explicitly saves a draft with `send=false`. No customer email is sent. The UI locks after success. API rejections allow correction/retry; an ambiguous network failure disables resubmission and asks the operator to check ERP first to reduce duplicate invoices.

The npm dependencies are development tools only and are not included in the deployed ZIP. ZET reports upstream development-dependency audit findings; no runtime npm libraries are shipped.

## Widget not showing

For an uploaded/installed ZIP, turn Developer Mode off in Settings → Developer Space → Widgets and refresh ERP. Developer Mode instead requires `npx zet run` on the local machine and a reachable HTTPS local manifest. This build registers both invoice list and invoice creation sidebar entry points, with modal presentation. The SDK requests a popup up to 1440 × 900 pixels, bounded by available screen size.

## Supplied ERP connection

The build now uses the supplied `erp_admin` connection and its exact generated connection metadata in the manifest. Organization ID is still obtained from the SDK; `sharedBy` is connection metadata, not an organization-ID override. Supplied scopes are `ERP.customer.ALL`, `ERP.invoices.ALL`, and `ERP.items.ALL`. With `userAccess: true`, each user must authorize the connection. Sales orders, taxes/settings, locations and salesperson lookups may require additional permissions; authorize those in Zoho before using those features. Custom-field mappings remain unconfigured. Live connection verification has not been performed.

## Authorization troubleshooting and popup sizing

The popup now requests at most 1160 × 680 CSS pixels, using the host viewport when accessible or conservative browser-window bounds. Content scrolls within the popup. The prior use of physical screen size was removed.

The supplied connection scopes do not match all documented REST endpoints: `/contacts` requires `ERP.contacts.READ`; items, taxes and locations use `ERP.settings.READ`; sales orders use `ERP.salesorders.READ`; invoice creation uses `ERP.invoices.CREATE`. Add these scopes to the actual authorized connection and reauthorize it for the current user. Editing manifest scope text alone cannot grant access. The manifest retains the supplied metadata until a newly generated connection JSON is available. If those scopes are not available in the ERP connection editor, ask Zoho support how to authorize the documented ERP v3 REST APIs. Also verify the connected user has access to the SDK-detected organization. Startup now checks customer/item API access and reports incomplete access instead of showing a false successful connection status.

Customer search now uses `contact_name_contains` and case-insensitive name matching to exclude unrelated returned records. Stale results are cleared immediately when typing. The UI uses compact spacing and smaller controls. The salesperson response-shape error shown in the tenant remains a separate integration issue; its lookup mapping still needs the actual response schema.
